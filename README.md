# Airport Investment Intelligence Agent

An AI-powered agent for airport investment analysis using public aviation data and deterministic scoring logic.

The project is focused on U.S. airport modernization and investment analysis. Operational flight analysis may also work for airports outside the U.S. when supported by AirLabs, while passenger and capacity analysis is currently U.S.-focused because it relies on BTS aviation data.

The system combines an OpenAI model for natural-language understanding, tool selection, conversational context, and explanation with Python-based analytical tools for congestion analysis, flight-haul distribution, expansion ranking, and demand-pressure analysis.

## Quick Start

From the project root:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

```bash

```

Open the local URL shown by Streamlit in the terminal.

## What the Project Does

The agent can answer questions such as:

- Which airports in New England are strong candidates for terminal expansion?
- Compare congestion levels between Los Angeles and Santa Ana airports.
- What percentage of flights departing Anchorage are long-haul?
- What is the unmet flight demand at SFO and why?

The agent also maintains conversation history, allowing follow-up questions such as:

```text
You: Compare LA and Santa Ana airport congestion levels.
You: Which one has the higher departure delay rate?
```

A lightweight Streamlit chat interface is included for interactive use, while the terminal interface remains available for direct CLI testing.

## Architecture

The project is implemented in Python and uses OpenAI tool calling.

The LLM is responsible for:

- Understanding user intent
- Selecting the appropriate analytical tools
- Maintaining conversational context
- Resolving follow-up questions
- Proposing airport candidates for broad geographic queries
- Explaining deterministic analytical results

The LLM does **not** calculate KPI values or rankings itself.

### Request Flow

```text
User Question
     ↓
OpenAI Agent
     ↓
Intent Understanding + Tool Selection
     ↓
Python Tool
     ↓
Relevant Data Source
(AirLabs / BTS / airportsdata)
     ↓
Normalization + Deterministic Analytics
     ↓
Tool Result
     ↓
OpenAI Agent
     ↓
Explanation + Follow-up Context
     ↓
User
```

The agent selects only the tools required for the current request.

Numerical KPIs and rankings are calculated in Python, while the LLM is responsible for orchestration, conversational context, and explanation.

## Data Sources

### AirLabs API

AirLabs provides operational flight data used for:

- Flight schedules
- Departure and arrival delays
- Cancellations
- Flight duration
- Observed flight activity

External data is normalized in Python before being used by the analytical tools.

AirLabs data represents a bounded operational sample rather than complete historical daily or monthly airport traffic totals. This means the agent does not use the operational sample to answer exact historical-count questions such as "How many flights landed yesterday?"

The AirLabs client also checks API error payloads explicitly. Provider failures, quota exhaustion, and similar errors are raised as data-source errors rather than being interpreted as an empty flight list. This prevents unavailable data from being reported as `0 flights`.

### BTS Aviation Data

BTS public aviation data provides passenger and seat-capacity information used for demand-pressure analysis.

This data is used to calculate metrics such as:

- Passenger totals
- Available seats
- Seat utilization
- Passenger growth
- Seat-capacity growth

BTS-based passenger and capacity analysis is limited to supported U.S. airports.

### airportsdata

The `airportsdata` package is used for:

- Resolving IATA and ICAO airport codes
- Validating airport locations
- Validating regional airport candidates

For broad regional questions, such as New England, the LLM proposes one representative major commercial airport candidate per state.

Regional expansion analysis then uses a deterministic Python wrapper that:

1. Validates each proposed airport code and location.
2. Ensures that at most one valid airport per state can enter the ranking.
3. Returns missing states instead of producing an incomplete regional ranking.
4. Passes only validated airports into the expansion-ranking function.

The "major commercial" characterization is part of the LLM-assisted candidate-selection step and is not independently verified against traffic-volume data.

## Deterministic Analytical Tools

All KPI calculations and rankings are implemented in Python rather than generated by the LLM.

The analytical layer includes:

- Departure congestion
- Arrival congestion
- Overall flight congestion
- Flight-haul distribution
- Direct expansion ranking
- Regional candidate validation and expansion ranking
- Unmet-demand scoring

General airport-congestion questions use the overall congestion calculation, while arrival-specific and departure-specific questions can use their dedicated tools.

This keeps numerical results reproducible and makes the scoring methodology explicit.

## Scoring Methodology

### Flight Congestion

Departure and arrival congestion are calculated independently.

For each direction:

```text
congestion_score =
    0.7 * delay_rate
    + 0.3 * normalized_average_delay
```

Where:

```text
normalized_average_delay =
    min(average_delay / 60, 1)
```

The overall flight congestion score is:

```text
flight_congestion_score =
    0.6 * departure_congestion
    + 0.4 * arrival_congestion
```

The score represents **operational flight congestion**.

It does not directly measure:

- Terminal crowding
- Gate utilization
- Runway queues
- Passenger waiting times

Cancellation rate is reported separately but is not currently included in the congestion score.

### Expansion Ranking

Airport expansion candidates are ranked using operational congestion and relative observed flight activity.

```text
expansion_score =
    0.6 * flight_congestion_score
    + 0.4 * normalized_flight_volume
```

Normalized flight volume is calculated relative to the airport with the highest observed flight count within the comparison set.

A higher congestion score increases the expansion score, while higher relative observed flight activity provides an additional signal of scale.

The result is a heuristic comparison. It does not prove that expansion is required or that an investment would be profitable.

For regional expansion questions, validation and ranking are combined in a deterministic regional tool so that invalid or duplicate-state candidates cannot enter the final ranking.

### Flight Haul Distribution

Flights are classified using deterministic duration thresholds:

```text
Short-haul:   < 180 minutes
Medium-haul:  180–359 minutes
Long-haul:    >= 360 minutes
```

Cancelled flights and flights without a valid duration are excluded from the distribution calculation.

### Unmet Demand

Unmet demand is modeled as a **demand-pressure proxy**, not as an exact estimate of unserved passengers.

The score combines:

- Seat utilization
- Passenger growth relative to seat-capacity growth
- Operational congestion

Seat utilization is converted to a bounded score:

```text
load_score =
    clamp(seat_utilization, 0, 1)
```

The passenger-versus-seat growth gap is:

```text
passenger_vs_seat_growth_gap =
    passenger_growth - seat_growth
```

The growth gap is then converted into a bounded score:

```text
capacity_gap_score =
    clamp(passenger_vs_seat_growth_gap / 0.10, 0, 1)
```

The final demand-pressure score is:

```text
unmet_demand_score =
    0.5 * load_score
    + 0.3 * capacity_gap_score
    + 0.2 * flight_congestion_score
```

A positive growth gap means passenger traffic is growing faster than seat capacity.

The score provides a demand-pressure signal but does not prove that the airport currently has insufficient physical capacity or represent an exact number of unserved passengers.

## Key Architecture Decisions

- **LLM for orchestration, Python for analytics:** the model interprets requests, selects tools, maintains conversational context, and explains results, while KPI calculations and rankings remain deterministic.
- **Specialized congestion tools:** general congestion, arrival congestion, and departure congestion are exposed separately so the agent can select the correct scope for the user's question.
- **Deterministic regional ranking:** regional validation and ranking are combined in one Python tool so only validated airports can enter the final ranking.
- **Multiple specialized data sources:** AirLabs is used for operational flight data, BTS for passenger and seat-capacity data, and `airportsdata` for airport resolution and geographic validation.
- **Explicit API failure handling:** external API error payloads are surfaced rather than interpreted as valid empty datasets.
- **Model configuration:** the prototype currently uses `gpt-4o-mini`, configured directly in the agent code. The model can be replaced without changing the analytical tools or deterministic scoring logic.
- **Direct APIs instead of MCP:** the prototype uses a small number of known integrations, so direct API calls keep the implementation simpler and easier to inspect and test.
- **No persistence layer:** conversation history is kept in memory, and no database or separate backend service is used because persistence is outside the scope of the assignment.
- **Streamlit for the chat UI:** Streamlit provides a lightweight conversational interface with minimal frontend overhead, allowing the prototype to focus on agent behavior, tool orchestration, and deterministic analytics.

## Tradeoffs and Limitations

- Multiple aviation sources are required because no single source provides all required operational, passenger, and capacity metrics.
- AirLabs data represents a limited current or scheduled operational window rather than long-term airport performance.
- AirLabs result limits may mean calculations use a bounded sample rather than every flight at very busy airports.
- AirLabs does not provide complete historical daily or monthly totals through the current integration.
- AirLabs account quotas, provider errors, or network failures can make operational data temporarily unavailable.
- Flight congestion is an operational delay-based proxy rather than a complete measure of airport congestion.
- Arrival delays may partially originate from conditions at the flight's departure airport.
- Cancellation rate is exposed as a metric but is not currently included in the congestion score.
- Congestion, expansion, and unmet-demand scores use heuristic weights rather than a trained statistical or economic model.
- Regional candidate selection is LLM-assisted rather than based on an exhaustive search of every airport in a region.
- Candidate airports are validated against airport metadata before ranking, and at most one candidate per state is retained for regional analysis.
- Regional ranking is only produced after the required regional candidate set is complete.
- The regional selection process may still omit airports that could be relevant investment candidates.
- The "major commercial" label used during regional candidate proposal is not independently validated against traffic-volume data.
- The expansion score measures relative signals within the evaluated candidate set and should not be interpreted as an ROI estimate.
- The unmet-demand score measures demand pressure rather than an exact number of unserved passengers or proof of insufficient physical capacity.
- Runtime queries and integration tests depend on external API availability and may fail because of provider availability, request quotas, rate limits, or network conditions.
- If a required external data source is unavailable, the system reports the limitation instead of treating the failure as zero activity or generating missing KPI values.
- Direct API integration keeps the prototype simple and makes deterministic scoring inputs easy to inspect and test. MCP would become more useful if the number and variety of integrations grew.

## Reliability Notes

The project intentionally distinguishes between:

- **No flights observed in a valid operational sample**
- **External data unavailable because of an API error**

These cases are not treated as equivalent.

If AirLabs returns a quota or provider error, the raw data layer raises an error rather than returning an empty list. This prevents downstream congestion, flight-haul, and expansion calculations from incorrectly treating an unavailable data source as zero flight activity.

Similarly, when a required source such as BTS is unavailable, the agent reports the limitation rather than fabricating or estimating a missing KPI.
